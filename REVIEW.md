# REVIEW.md: Analysis of Starter Code Defects

The starter codebase in `app/main.py` contained multiple critical defects spanning timezone mismanagement, concurrency vulnerabilities, incorrect business rule calculations, data validation gaps, and unindexed queries. Below is the review table documenting each identified defect, its concrete failure symptom, and the fix applied.

---

## 1. Identified Defects & Applied Fixes

| # | Where (function / line) | What is wrong | How you'd notice it | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_work_hours` (lines 40–41) | Line 41 used Python's native `round(seconds / 3600, 2)`, which applies banker's rounding (round-half-to-even) and rounds .005 down to the nearest even digit instead of rounding half-up. | A punch duration of 16,218 seconds (4.505 hours) computes to `4.5` instead of `4.51`. | Replaced float division with `Decimal(delta_sec) / Decimal(3600)` quantized with `ROUND_HALF_UP` to two decimal places. |
| 2 | `compute_late_minutes` (lines 33–37) | Lines 36–37 computed `minutes = int(delta_seconds / 60)` and checked `minutes > 10`. A punch-in 1 second after 09:40:00 is treated as on time instead of 10 minutes late because 601 seconds floors to 10 minutes, failing the `> 10` check. | A punch-in timestamp at `09:40:01` on a `09:30` shift (601 seconds elapsed) reports `0` late minutes instead of `10`. | Changed the condition to evaluate `delta_seconds > 600` directly before computing `delta_seconds // 60`. |
| 3 | `compute_overtime` (line 46) | Attached `tzinfo=IST` to shift end datetime while `punch_out` was naive, causing mixed naive and aware datetime subtraction. | Calling `compute_overtime` with a naive datetime raises `TypeError: can't subtract offset-naive and offset-aware datetimes`. | Normalized all timestamps to aware UTC datetimes before computing intervals. |
| 4 | `compute_overtime` (line 46) | Constructed shift end directly from the punch-in date string without adding a day for overnight shifts ending on the following day. | Punch-out at `06:40` on July 7 for an overnight shift (`22:00`–`06:00` starting July 6) yields `1480` minutes (24.7 hours) of overtime instead of `40` minutes. | Added `+ timedelta(days=1)` to `shift_end_dt` whenever `shift_end < shift_start`. |
| 5 | `compute_overtime` (line 47) | Returned elapsed minutes without enforcing Rule R3, which requires overtime to be at least 30 minutes. | Punching out 15 minutes past shift end (`18:45` on an `18:30` shift) awards `15` minutes of overtime instead of `0`. | Added a threshold check returning overtime only when `delta_minutes >= 30`, else `0`. |
| 6 | `punch_in` (lines 100–101, 113) | Looked up the employee and directly accessed `emp["shift_start"]` without checking if `emp` was `None`. | Calling `POST /attendance/punch-in` with an unknown `emp_code` crashes with HTTP 500 (`TypeError: 'NoneType' object is not subscriptable`). | Looked up employee first and raised `HTTPException(404, "Employee not found")` if missing. |
| 7 | `PunchInIn` / `punch_in` (lines 63–67, 102) | `punched_at` had no integer magnitude bounds and divided seconds by 1000, accepting second-based epoch timestamps. | Sending `POST /attendance/punch-in` with `"punched_at": 1783312500` (seconds) returns HTTP 201 with stored date in year 1970 (`"1970-01-21"`). | Added strict integer range validation `[100_000_000_000, 4_102_444_800_000]` rejecting seconds, floats, and invalid types with HTTP 422. |
| 8 | `PunchInIn` / `punch_in` (line 66) | `status` was typed as an unconstrained `str = "PRESENT"`, accepting non-presence statuses like `ABSENT` or `LEAVE`. | Sending `POST /attendance/punch-in` with `"status": "LEAVE"` returns HTTP 201 and stores a bogus leave punch. | Restricted `status` to presence enums (`PRESENT`, `WFH`, `ON_DUTY`), returning HTTP 422 for all other values. |
| 9 | `punch_in` (lines 102–103) | Used `datetime.fromtimestamp(...)` in server local time instead of IST to determine the calendar attendance date. | A punch at `01:00 AM IST` on July 7 (`19:30 UTC` on July 6) on a UTC server stores date `"2026-07-06"` instead of `"2026-07-07"`. | Converted epoch ms to aware UTC and evaluated the calendar date in IST per Rule R1. |
| 10 | `create_employee` (lines 78–85) | Used check-then-insert (`find_one` followed by `insert_one`) without a database uniqueness constraint, allowing concurrency race conditions. | Concurrent `POST /employees` requests with the same `emp_code` both succeed with HTTP 201 and insert duplicate employee documents. | Added unique index on `employees.emp_code`, catching `DuplicateKeyError` to return HTTP 409. |
| 11 | `list_employees` (lines 89–96) | Computed `skip = page * page_size` (skipping page 1), and counted the entire collection ignoring the department filter `q`. | Calling `GET /employees?page=1&page_size=20` returns records 21–25 (first 20 missing), and `?department=HR` returns total count of all employees instead of matching department count. | Corrected skip calculation to `(page - 1) * page_size` and counted filtered documents using `count_documents(q)`. |
| 12 | `EmployeeIn` (lines 53–61) | Lacked field validation regexes, email validation, shift time divergence checks (`shift_start != shift_end`), and calendar date verification. | `POST /employees` accepted malformed payloads like `{"emp_code": "bad", "email": "not-an-email", "shift_start": "09:00", "shift_end": "09:00", "joined_on": "2026-02-30"}` with HTTP 201. | Added Pydantic field validators with regexes, verified `shift_start != shift_end`, and strictly parsed calendar dates with `datetime.strptime`. |
| 13 | `punch_in` (line 119) | Added `doc["id"] = str(res.inserted_id)` and left timestamps as datetime objects serialized as ISO strings. | Response leaked internal MongoDB `id` string and returned ISO strings instead of integer epoch milliseconds, violating OpenAPI `AttendanceRecord` schema. | Stripped internal IDs and mapped all timestamp fields to integer epoch milliseconds. |
| 14 | `list_attendance` (lines 124–150) | Loaded entire collection into memory with `list(find())` and sorted in Python; did not validate that `date_from <= date_to`. | Queries on large datasets cause memory spikes and high latency; passing inverted range `date_from=2026-07-10&date_to=2026-07-01` executes silently instead of returning an error. | Implemented database-level sorting backed by `(date: -1, emp_code: 1)` indexes, and validated `date_from <= date_to` (returning 422 if inverted). |
| 15 | `/health` (lines 72–74) | Returned static `200 {"status": "ok"}` without verifying database connectivity. | Calling `GET /health` with MongoDB stopped returned `200 OK`, masking database outages. | Added `client.admin.command("ping")` inside a try/except block returning `503 Service Unavailable` on database failure. |
| 16 | `MongoClient(...)` (line 22) | Initialized client without `tz_aware=True`, causing PyMongo to return naive UTC datetimes. | Comparing or subtracting database timestamps against aware UTC datetimes raises `TypeError: can't subtract offset-naive and offset-aware datetimes`. | Initialized `MongoClient(..., tz_aware=True, tzinfo=timezone.utc)`. |

## 2. Items Examined and Determined Not to Be Defects

1. **Synchronous endpoint definitions (`def`) with PyMongo**: FastAPI offloads standard `def` functions to an AnyIO threadpool worker pool, preventing synchronous PyMongo calls from blocking the main asyncio event loop.
2. **`load_dotenv()` default behavior**: By default in `python-dotenv`, `override=False`, meaning existing operating system environment variables (such as injected production `MONGO_URI`) take strict precedence over `.env` defaults.
3. **Absence of single-field index on `status`**: The `status` field has only 5 values (low cardinality). A single-field index has poor selectivity and slows writes; compound index `(status, date, emp_code)` covers status-filtered date queries cleanly.
